# CStudio 역할 전환 UI 구조안 v1

## 목적

이 문서는 `cstudio`를 여러 사용자 계층과 역할을 담는 통합 워크스테이션으로 확장하기 위한 UI 구조 초안이다.

방향은 두 가지를 동시에 만족해야 한다.

- 전체적인 셸 감각은 `Rider` 계열 IDE처럼 안정적이어야 한다
- 사용자 역할과 권한에 따라 서로 다른 메인 화면으로 전환될 수 있어야 한다

## 핵심 판단

`cstudio`의 UI는 “셸은 고정, 역할 워크스페이스만 전환”하는 구조가 맞다.

즉 앱 전체를 매번 다른 제품처럼 바꾸는 것이 아니라, 하나의 안정적인 IDE형 셸 안에서 메인 작업 컨텍스트만 바뀌어야 한다.

이 구조를 여기서는 `Role Workspace Carousel over Stable Shell`이라고 부른다.

## 다루는 역할

초기 기준으로 다음 역할 워크스페이스를 상정한다.

- `Pipeline Authoring`
- `Pipeline Analysis`
- `Tool Administration`
- `K8s Operations`

중요한 점은 “역할”과 “사람”을 1:1로 고정하지 않는 것이다.

- 한 사용자가 여러 워크스페이스에 접근할 수 있다
- 조직에 따라 역할이 분리될 수 있다
- 권한에 따라 일부 워크스페이스는 숨기거나 잠글 수 있다

즉 `cstudio`는 다중 페르소나 앱이 아니라, 다중 역할 워크스페이스를 담는 단일 앱으로 본다.

## 상위 UX 원칙

### 1. 셸은 항상 익숙해야 한다

상단 크롬, 좌측 탐색, 중앙 문서 호스트, 우측 패널, 하단 상태/로그라는 큰 틀은 유지한다.

사용자는 역할이 바뀌어도 앱을 다시 배우면 안 된다.

### 2. 전환은 강하지만 과하지 않아야 한다

워크스페이스가 바뀌면 성격은 분명히 달라져야 한다. 다만 정보구조까지 뒤집으면 안 된다.

즉 “다른 메인 화면”처럼 느껴지되, 길을 잃지 않게 해야 한다.

### 3. 방향키 회전은 주 내비게이션이 아니라 상위 전환 장치다

사용자가 제안한 좌우 회전 개념은 유효하다. 다만 이 제스처는 문서 탭, 트리 탐색, 캔버스 조작과 충돌하지 않도록 최상위 워크스페이스 전환에만 사용해야 한다.

### 4. 권한은 라우팅 규칙으로 반영한다

접근 가능한 워크스페이스 집합은 사용자 또는 실행 컨텍스트에 따라 달라질 수 있다.

- 허용된 워크스페이스만 순환 대상으로 포함
- 금지된 워크스페이스는 숨김 또는 잠금 표시
- 직접 URL 같은 개념이 생겨도 진입 시 권한 검사를 먼저 수행

## 제안 구조

### 셸 레벨

모든 역할이 공유하는 고정 셸이다.

- 상단: 앱 제목, 메뉴, 현재 워크스페이스 이름, 권한/환경 배지
- 좌측: 현재 워크스페이스 전용 탐색 구조
- 중앙: 해당 역할의 주 작업 문서 또는 대시보드
- 우측: 현재 선택 대상의 속성/인스펙터/실행 액션
- 하단: 상태, 로그, 진단, 백그라운드 작업

즉 바뀌는 것은 셸이 아니라 셸 내부의 콘텐츠 조합이다.

### 역할 전환 레벨

역할 전환은 앱의 최상위 모드 전환이다.

- 현재 워크스페이스를 좌우로 이동하며 전환
- 순환 대상은 사용자가 접근 가능한 워크스페이스만 포함
- 전환 시 새 역할에 맞는 좌측 트리, 중앙 기본 문서, 우측 패널 구성이 로드됨

이 전환은 macOS의 공간 전환처럼 “옆 화면으로 넘어간다”는 감각을 줄 수 있다. 다만 실제 구현은 전체 창을 날리는 전환보다, 중앙 작업영역과 워크스페이스 크롬이 수평 이동하는 정도가 적절하다.

## 전환 UI 제안

### 기본안

`Rider` 감각을 유지하려면 전환 장치를 과하게 전면에 두지 않는 편이 좋다.

권장 위치는 두 곳이다.

- 상단 크롬의 현재 워크스페이스 라벨 주변
- 하단 상태바의 좌우 끝 일부

표현은 다음과 같이 단순하게 간다.

- `< Pipeline Authoring >`
- `1 / 4`
- 현재 워크스페이스 색상 포인트 또는 아이콘

### 조작 방식

- 마우스: `<` / `>` 버튼 클릭
- 키보드: 명시적 단축키로 좌우 전환
- 선택형 드롭다운 또는 팝업: 직접 특정 워크스페이스로 점프

중요한 점은 일반 방향키를 그대로 쓰면 안 된다는 것이다.

캔버스, 리스트, 트리, 테이블이 많은 앱이므로 기본 화살표 키는 현재 포커스 영역의 입력으로 남겨야 한다.

권장 방식은 다음 중 하나다.

- `Ctrl/Cmd + Alt + Left/Right`
- `Ctrl/Cmd + [/ ]`
- 전용 커맨드 팔레트 액션

즉 “방향키 감각”은 살리되, 실제 입력은 충돌 없는 명시적 단축키로 가는 것이 안전하다.

## 역할별 메인 화면 초안

### Pipeline Authoring

제작 중심 워크스페이스다.

- 좌측: 그래프 자산, 노드 팔레트, 템플릿, 프로젝트 트리
- 중앙: `DagEdit` 기반 그래프 편집 문서
- 우측: 노드/엣지/그래프 속성
- 하단: validation, build, execution preview

핵심 감각은 IDE 안의 에디터 워크스페이스다.

### Pipeline Analysis

분석 중심 워크스페이스다.

- 좌측: 실행 세션, 저장된 리포트, 비교 대상
- 중앙: 결과 문서, 실행 추적, 시각화, 그래프 리드온리 탐색
- 우측: 선택된 결과의 상세 메타데이터
- 하단: 이벤트, 경고, 성능 로그

핵심 감각은 조사와 비교를 위한 인스펙션 워크스페이스다.

### Tool Administration

관리자 authoring과 검증 중심 워크스페이스다.

- 좌측: 도구 목록, 등록 상태, validation queue
- 중앙: 도구 정의 문서, 설정 편집, 정책 편집 화면
- 우측: 배포 조건, 입력/출력 스키마, 권한 정책
- 하단: validation 결과, build/register 로그

핵심 감각은 편집기와 운영 콘솔의 중간 지점이다.

### K8s Operations

운영 관찰과 제어 중심 워크스페이스다.

- 좌측: cluster, namespace, workload, resource 트리
- 중앙: 상태 대시보드, 로그, 객체 상세 문서, 이벤트 뷰
- 우측: 선택 리소스 속성, 액션, health 정보
- 하단: stream log, event timeline, diagnostics

핵심 감각은 IDE 셸을 유지한 운영 콘솔이다.

## 권한 모델과 UI 반영

권한은 단순히 버튼 비활성화로 끝내면 안 된다. 워크스페이스 진입 구조 자체에 반영돼야 한다.

### 허용 워크스페이스만 노출

가장 단순하고 안전한 기본 정책이다.

- 접근 가능한 워크스페이스만 회전 대상에 포함
- 사용자는 자신이 볼 수 없는 영역의 존재를 굳이 알 필요가 없음

### 잠금형 노출

조직 정책상 역할의 존재를 알려야 하는 경우 사용할 수 있다.

- 회전 목록에는 보이되 잠금 배지 표시
- 클릭 시 권한 안내 또는 요청 흐름 제공

초기 버전에서는 숨김 정책이 더 현실적이다.

## 왜 이 구조가 Rider와 양립 가능한가

핵심은 `Rider`의 강점이 “복잡한 기능을 한 셸 안에 안정적으로 담는 것”에 있기 때문이다.

즉 `cstudio`가 Rider의 감각을 가져오려면, 모든 화면이 제각각인 다중 앱처럼 보여서는 안 된다. 오히려 셸 프레임은 안정적으로 유지되고, 그 안의 워크스페이스만 달라져야 한다.

이 구조는 다음을 동시에 만족한다.

- 상위 구조는 IDE처럼 일관됨
- 역할별 업무 밀도와 문맥은 분리됨
- 한 사용자가 여러 역할을 가질 때 빠르게 넘나들 수 있음
- 권한에 따라 노출 범위를 제한할 수 있음

## 추천 상호작용 요약

- 셸은 유지한다
- 역할 워크스페이스만 좌우 회전한다
- 일반 방향키는 쓰지 않는다
- 명시적 단축키와 `< >` 버튼을 함께 둔다
- 전환 시 전체 창보다 워크스페이스 콘텐츠가 옆으로 미끄러지는 느낌을 준다
- 권한 없는 워크스페이스는 기본적으로 숨긴다

## v1 이후 후속 설계 항목

이 문서 다음 단계에서 정리할 주제는 다음과 같다.

1. 워크스페이스 전환 상태 모델
2. 역할별 좌측 탐색 구조 상세
3. 중앙 문서 호스트에서 역할별 기본 랜딩 화면 정의
4. 권한별 노출 정책과 세션 초기 진입 규칙
5. 전환 애니메이션과 포커스 복원 규칙

## 결론

사용자가 제안한 “채널 돌리듯 화면을 넘기는 감각”은 `cstudio`에 잘 맞을 수 있다.

다만 그것은 앱 전체를 계속 회전시키는 UI가 아니라, 안정적인 Rider형 셸 위에서 역할 기반 메인 워크스페이스를 넘기는 상위 전환 장치로 써야 한다.

이 방향이면 다음 두 요구를 동시에 만족할 수 있다.

- 통합 워크스테이션으로서 여러 역할을 한 앱에 담는다
- 사용자와 권한에 따라 노출되는 메인 화면을 제어한다
