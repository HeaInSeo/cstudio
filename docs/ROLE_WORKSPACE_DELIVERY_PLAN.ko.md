# CStudio 역할 워크스페이스 개발 일정안 v1

## 목적

이 문서는 [ROLE_WORKSPACE_UI_V1.ko.md](./ROLE_WORKSPACE_UI_V1.ko.md) 설계안을 실제 `cstudio` 구조 개발로 옮기기 위한 단계별 일정안이다.

현재 기준점은 Sprint 05 완료 상태다. 즉 이 일정은 “단일 셸 + DagEdit 샘플 어댑터” 상태에서 “역할 전환이 가능한 통합 워크스테이션 셸”로 가기 위한 구현 계획이다.

## 일정 원칙

이번 작업은 한 번에 모든 역할 화면을 완성하는 방식으로 가면 안 된다.

우선순위는 다음 순서를 따른다.

1. 셸 전환 기반 먼저
2. 권한과 노출 규칙 다음
3. 역할별 워크스페이스는 얇은 vertical slice로 순차 구현
4. 분석기와 경고 기준은 각 단계마다 유지

즉 “기반 구조 -> 첫 전환 동작 -> 역할별 콘텐츠” 순서로 진행한다.

## 제안 일정

### Sprint 06A - Workspace Transition Foundation

목표는 역할 전환이 가능한 셸 기반을 추가하는 것이다.

- `RoleWorkspace` 개념 도입
- 현재 활성 워크스페이스 상태 모델 추가
- 좌우 전환 명령과 `< >` 전환 UI 추가
- 현재 워크스페이스별 제목, 배지, 기본 레이아웃 차등 노출
- 기존 단일 셸 데이터를 역할별 샘플 데이터로 분리할 준비

완료 기준:

- 앱이 하나의 고정 셸 위에서 최소 2개 이상의 워크스페이스를 전환할 수 있다
- 문서, 좌측 탐색, 우측 패널, 하단 상태가 전환 시 함께 교체된다
- 기본 단축키와 버튼 클릭 모두 동작한다

산출물:

- 새로운 코어 상태 모델
- 전환 가능한 메인 뷰모델 구조
- 스크린샷 문서 초안

예상 기간:

- 1 sprint

### Sprint 06B - Role Visibility And Authorization Surface

목표는 역할 노출 규칙과 접근 제어를 셸 전환 모델에 반영하는 것이다.

- 허용된 워크스페이스 집합 모델 추가
- 숨김형 노출 정책 구현
- 잠금형 노출이 필요한 경우를 위한 확장 포인트 설계
- 초기 진입 워크스페이스 결정 규칙 추가
- 권한 없는 워크스페이스 직접 진입 방지 규칙 정리

완료 기준:

- 사용자 컨텍스트 또는 세션 설정에 따라 노출 워크스페이스 집합이 달라진다
- 권한 없는 워크스페이스는 기본적으로 순환 대상에서 제외된다
- 현재 워크스페이스 전환 로직이 권한 규칙을 깨지 않는다

산출물:

- 접근 정책 문서
- 권한별 샘플 세션 구성
- 숨김 정책 기준 UI 정리

예상 기간:

- 1 sprint

### Sprint 07A - Pipeline Authoring Workspace Slice

목표는 첫 실사용 중심 워크스페이스를 올리는 것이다.

- `Pipeline Authoring` 전용 좌측 탐색 구조 추가
- 중앙 기본 화면을 `DagEdit` 중심 편집 워크스페이스로 고정
- 우측 속성 패널을 제작 작업 기준으로 정리
- 하단 패널에 validation/build 관련 슬롯 추가

완료 기준:

- Authoring 워크스페이스가 독립된 메인 화면처럼 동작한다
- 기존 `DagEdit` 임베드 경로가 이 워크스페이스에 자연스럽게 통합된다
- 다른 워크스페이스와 전환해도 셸 구조는 유지된다

산출물:

- 첫 역할 기반 vertical slice
- Authoring 전용 스크린샷 문서

예상 기간:

- 1 sprint

### Sprint 07B - Pipeline Analysis Workspace Slice

목표는 분석 중심 워크스페이스를 추가하는 것이다.

- 실행 세션/리포트 중심 좌측 탐색 추가
- 중앙 분석 문서 랜딩 화면 추가
- 비교/조사형 우측 패널 구조 추가
- 하단 이벤트/경고/성능 로그 성격으로 재구성

완료 기준:

- Authoring과 시각적/기능적 성격이 다른 Analysis 워크스페이스가 제공된다
- 같은 셸 안에서 제작과 분석이 빠르게 전환된다
- 공용 셸 계약을 깨지 않고 확장된다

예상 기간:

- 1 sprint

### Sprint 08A - Tool Administration Workspace Slice

목표는 관리자 authoring과 정책 관리 워크스페이스를 추가하는 것이다.

- 도구 목록/등록 상태/검증 흐름 중심 탐색 추가
- 설정, 정책, 등록 관련 문서 화면 추가
- 우측 패널에 스키마/배포 조건/권한 정보 반영
- 하단에 validation 및 register 로그 반영

완료 기준:

- 관리자 역할이 일반 제작/분석과 구분되는 메인 화면을 가진다
- 향후 NodeKit 연계나 admin adapter 추가가 가능한 구조를 유지한다

예상 기간:

- 1 sprint

### Sprint 08B - K8s Operations Workspace Slice

목표는 운영 관찰용 워크스페이스를 추가하는 것이다.

- 클러스터/네임스페이스/워크로드 중심 좌측 탐색 추가
- 중앙에 운영 대시보드 및 리소스 문서 랜딩 추가
- 우측 health/action 패널 정의
- 하단 stream log/event/diagnostics 구획 정의

완료 기준:

- 운영 워크스페이스가 Rider형 셸 안에서도 독립된 성격을 가진다
- authoring/admin과 다른 데이터 밀도와 운영 감각이 표현된다

예상 기간:

- 1 sprint

### Sprint 09 - Stabilization And Composition Cleanup

목표는 역할 워크스페이스 구조를 정리하고 장기 확장 기반을 다지는 것이다.

- 수동 조합 루트 정리
- 역할별 서비스 조합 구조 정리
- 중복 UI 조각 및 샘플 데이터 구조 정리
- 테스트 가능 지점과 정적 분석 회귀 점검
- 스크린샷 및 문서 정리

완료 기준:

- 역할 워크스페이스 구조가 더 추가돼도 셸 전체 수정이 최소화된다
- 경고 증가 없이 안정적으로 빌드된다
- 다음 실제 도메인 어댑터 작업을 받을 준비가 된다

예상 기간:

- 1 sprint

## 전체 기간 요약

현실적인 최소 일정은 다음과 같다.

- 기반 구조: 2 sprints
- 핵심 워크스페이스 2개: 2 sprints
- 관리자/운영 워크스페이스 2개: 2 sprints
- 안정화: 1 sprint

즉 총 7 sprints를 기본선으로 잡는 것이 적절하다.

더 공격적으로 줄이려면 다음이 가능하다.

- `Tool Administration`과 `K8s Operations`를 스켈레톤 화면으로 먼저 넣고 이후 심화
- Analysis/Admin 일부를 같은 공용 문서 호스트 규칙 위에 얇게 시작

그 경우 5 sprints까지 압축은 가능하지만, 현재 코드가 아직 단일 셸 중심이라는 점을 감안하면 7 sprint 계획이 더 안전하다.

## 구현 순서 추천

지금 바로 개발을 시작한다면 순서는 다음이 맞다.

1. `RoleWorkspace` 상태 모델과 전환 명령 추가
2. 메인 뷰모델을 역할 전환 가능한 조합 구조로 재편
3. `Pipeline Authoring`을 첫 실제 워크스페이스로 승격
4. 권한/노출 규칙 연결
5. `Pipeline Analysis` 추가
6. `Tool Administration` 추가
7. `K8s Operations` 추가
8. 안정화 및 조합 정리

핵심은 `DagEdit`가 이미 있으므로, 첫 vertical slice는 반드시 `Pipeline Authoring`으로 잡는 것이다.

## 리스크

### 1. 현재 뷰모델 구조는 단일 워크스페이스 전제다

지금 `MainWindowViewModel`은 단일 서비스 조합을 소비하는 구조다. 역할 전환을 제대로 넣으려면 서비스 집합 전환 또는 상위 워크스페이스 상태 계층이 추가돼야 한다.

### 2. 샘플 데이터와 실제 어댑터 경계가 다시 정리돼야 한다

현재는 `Mock`과 `DagEditAdapter`가 공존하지만, 역할별 워크스페이스가 생기면 “어떤 역할이 어떤 어댑터/샘플을 쓰는지”를 묶는 새 조합 계층이 필요하다.

### 3. 권한은 뒤늦게 붙이면 셸 구조를 다시 흔든다

권한 모델은 UI 후반이 아니라 전환 구조 초기에 넣어야 한다.

### 4. 운영 워크스페이스는 정보 밀도가 다르다

`K8s Operations`는 편집기 중심 UI와 성격이 다르므로, 공용 셸 계약을 유지하면서도 다른 밀도를 담는 슬롯 구조가 필요하다.

## 권장 보고 결론

현재 설계안으로 개발을 진행하는 것은 타당하다. 다만 구현은 “네 역할 화면을 한 번에 추가”가 아니라 “역할 전환 가능한 셸 기반을 먼저 만들고, Authoring부터 vertical slice로 올리는 방식”으로 가야 한다.

따라서 현재 기준 권장 일정은 다음과 같다.

- 최소 권장: 7 sprints
- 압축 가능: 5 sprints
- 첫 개발 착수 범위: `Sprint 06A Workspace Transition Foundation`

즉 다음 실제 개발 작업은 `역할 전환 상태 모델 + 전환 UI + 최소 2개 워크스페이스 전환`까지를 첫 배치로 잡는 것이 맞다.
